# COGUX 기록: 찻잎상회 결제 화면

## 1. 프로젝트 읽기

| 번호 | 항목 | 내용 | 근거 |
|---|---|---|---|
| U1 | 사용자 | 처음 구매하는 손님, 결제 안전에 불안을 느낌 | README.md 사용자 진술 |
| U2 | 사용 환경 | 휴대폰, 모바일 우선 | README.md 제약 |
| T1 | 주요 과업 | 배송지 입력, 결제 수단 선택, 34,000원 결제, 주문 접수 확인 | README.md 주요 과업 |
| S1 | 핵심 화면 | 한 장에 모든 입력이 있는 결제 화면 | index.before.html 전체 |
| S2 | 현재 문제 | 선택지 14개가 한 화면, 버튼 높이 28px, 오류 문구가 "잘못된 입력"뿐 | index.before.html 줄 9~17 |
| C1 | 제약 | 백엔드 없는 단일 HTML, 초록 계열 브랜드 | README.md 제약 |
| C2 | 전화번호 입력 | 고객이 번호 적는 방법을 자주 묻는다 | README.md 사용자 진술 |
| U3 | 후기·평점 데이터 | 검증 가능한 후기 데이터는 없다 (assumed) | 근거 없음 |

## 2. 선택한 원칙

| 원칙 | 근거 | 적용 이유 |
|---|---|---|
| `choice-overload` | S2, U1 | 처음 온 손님에게 동등한 선택지 14개는 결정을 막습니다. 수단을 3개로 줄입니다. |
| `goal-gradient-effect` | T1, U1 | 단계가 있는 과업이라 진척이 보이면 끝까지 갈 동기가 생깁니다. |
| `fitts-law` | U2, S2 | 휴대폰에서 28px 버튼은 오탭이 납니다. 주요 버튼을 키웁니다. |
| `postels-law` | C2 | 번호를 어떻게 적느냐는 문의가 있어 입력 형식을 너그럽게 받습니다. |
| `error-prevention-and-recovery` | S2 | "잘못된 입력"은 고칠 방법을 말하지 않습니다. 원인과 예시를 줍니다. |
| `feedforward` | U1, T1 | 결제 전에 무슨 일이 일어날지 알려야 불안이 줄어듭니다. |
| `peak-end-rule` | T1 | 결제 완료 화면이 경험의 마지막 인상이 됩니다. |
| `jakobs-law` | U1 | 처음 온 손님은 다른 쇼핑몰의 결제 순서(배송, 결제, 확인)를 기대합니다. |

## 3. 제외한 원칙

| 원칙 | 제외 이유 |
|---|---|
| `social-proof` | 검증 가능한 후기 데이터가 없습니다(U3). 가짜 후기는 쓰지 않습니다. |
| `loss-aversion` | 결제 흐름에서 가짜 기한으로 압박하는 용도로 흐르기 쉽습니다. 이 프로젝트에는 필요하지 않습니다. |
| `flow` | 2분짜리 일회성 거래라 몰입이 목표가 아닙니다. |
| `zeigarnik-effect` | 이어 하기가 필요한 과업이 아니고, 미완성 표시로 압박하지 않습니다. |
| `working-memory` | 3단계 모두 이전 정보를 외울 필요가 없고 확인 단계에 요약이 있습니다. |

## 4. 설계 결정

| 원칙 | 화면 | 변경 | 관찰 확인 |
|---|---|---|---|
| `choice-overload` | 결제 방법 | 기본 3개만 보이고 나머지는 접어 둠 | 결제 단계에서 보이는 라디오가 3개 이하 |
| `goal-gradient-effect` | 상단 | 3단계 표시와 "N단계 / 3단계" 문구 | 현재 단계 문구가 실제 단계와 일치 |
| `fitts-law` | 모든 주요 버튼 | 높이 48px 이상, 전체 폭 | 각 주요 버튼 높이 48px 이상 |
| `postels-law` | 휴대폰 | 공백과 하이픈이 섞여도 숫자만 남겨 허용 | "010 1234-5678" 입력이 거절 없이 01012345678로 정리됨 |
| `error-prevention-and-recovery` | 오류 문구 | 원인, 고치는 방법, 예시를 함께 | 오류 문구에 "예:" 또는 방법 문장이 있음 |
| `feedforward` | 결제 버튼 | 금액이 적힌 버튼과 결제 전 확인 화면 | 확인 화면의 버튼 문구에 금액이 있고 설명이 있음 |
| `peak-end-rule` | 완료 | 주문번호와 도착 시기, 다음 행동 | 완료 화면에 주문번호와 다음 버튼이 있음 |
| `jakobs-law` | 흐름 | 배송, 결제, 확인 순서 | 단계 이름이 이 순서임 |

## 5. 구현

수정한 파일은 `index.html` 하나입니다(원본은 `index.before.html`로 보존). 테마 전환은 이 저장소용으로 직접 쓴 해·달 스위치입니다. 한국어 줄바꿈 규칙과 모바일 폭을 적용했습니다. 실행한 게이트는 아래 6항에 있습니다.

## 6. 검증 결과

검증은 agent-browser 헤드리스 세션으로 폭 375px에서 실행했습니다. 수정 전 원본의 값은 괄호에 적었습니다.

| 관찰 확인 | 결과 |
|---|---|
| 결제 단계 라디오 3개 이하 | 통과: 3개 (원본은 선택지 14개) |
| 단계 문구 일치 | 통과: 1단계에서 "1단계 / 3단계", 이동 후 "2단계 / 3단계" |
| 주요 버튼 48px 이상 | 통과: 48px (원본 28px) |
| 번호 정리 | 통과: "010 1234-5678"이 "01012345678"로 정리되고 다음 단계로 이동 |
| 오류 문구에 방법 | 통과: 이름 누락 시 "이름을 입력해 주세요. 받는 분 이름으로 배송됩니다." (원본은 "잘못된 입력"). 번호 오류 문구에는 예시가 있으나 이 문구는 직접 실행하지 않았습니다. |
| 결제 버튼 금액 | 통과: "34,000원 결제하기" |
| 완료 화면 | 통과: 주문번호 CH- 형식 표시, 쇼핑 계속하기 버튼 존재 |
| 가로 넘침 없음(375px) | 통과 |
| 테마 전환 동작 | 통과: 클릭하면 data-theme이 dark에서 light로 바뀜 |

## 7. 미확인 항목

- 키보드 조작 순서, 초점 표시, 200% 확대, 320px과 768px 폭은 확인하지 않았습니다.
- 색 대비는 측정하지 않았습니다.
- 두 번째 번호 오류 문구와 주소 누락 문구는 직접 실행하지 않았습니다.
- 사용자를 대상으로 한 시험은 하지 않았습니다. 이 기록은 설계 근거와 관찰 확인까지만 증명합니다.
